# Decisions and unresolved design details

## Foundation, 2026-10-20

- Package names are `picket-core`, `picket-app`, and `picket-cli`; the CLI binary is `picket`. Prefixes avoid ambiguity with Rust's built-in core library.
- Keep the original supplied design unchanged under ignored local storage. The repository copy is docs/design.md, with personal author metadata omitted and punctuation normalized. Product and package names use Picket.
- The setup branch established the environment and runnable shell. The remaining M1 native notification action investigation was completed in PR #5; later product features remain outside the foundation.
- Pin the installed Rust toolchain, Node, pnpm, direct frontend packages, lockfiles, and CI actions. Use a single pnpm workspace and a single Cargo workspace.
- Do not create the OpenClaw package until real upstream hook names and payloads are verified in M6.
- Keep the public project license undecided until the Messages decoder dependency is reviewed. Do not add a possibly GPL decoder while implying an MIT or Apache-only distribution.
- Delay model download and llama.cpp integration until the mock pipeline is evaluated, as required by the design's milestone order. CMake and Clang are available for that build.
- Do not add empty subsystem source modules, fabricated evaluation metrics, or disabled CI gates. Document the directory's future boundary instead.
- Use stderr tracing for the current data-free shell. Before handling account data, add tested redaction and size-based rotation; tracing alone is not a privacy filter.
- Generate the simple temporary app icon from `assets/icon.svg` with `pnpm tauri icon ../../assets/icon.svg --output icons`; do not manually edit generated icons or Tauri schemas.

## Alignment review, 2026-10-21

- [Alignment engine plan](alignment-engine-plan.md) records the focused review, evidence policy, implementation increments, experiments, evaluation gates and unsolved limits. The related sections of `design.md` reflect it. This review initially added no product code; subsequent M2 and M3 implementation is recorded below.
- Separate observable account state, actor evidence, request fit and alert routing. Remove the old 0.95 claim attribution, 0.30 effects-only baseline, automatic `user` fallback and additive authorization score. Unknown actor is a first-class outcome; a claim or a known contact cannot grant permission.
- Explicit restrictions are gates. Preserve missing fields, conflicting evidence, task revisions, cardinality and collection coverage. An AI extraction is an uncertain input; no AI judge changes v1 verdicts. Expectedness feedback does not automatically label actors, trust contacts or tune thresholds.
- Header fingerprinting is an unvalidated experiment, not actor proof. Personal Gmail's documented message resource does not expose the sending app. Workspace Gmail logs do document app identity and message identifiers, correcting the earlier conversation's overly pessimistic assessment; real API/export availability and unique joins remain unverified. Workspace integration is future scope and adds no permissions now.
- Current OpenClaw documentation identifies `after_tool_call`, but optional result/error fields and harness-specific coverage require an installed-version, per-tool experiment. Treat runtime-linked reports as conditional on runtime integrity, not near-certain independent attribution.
- Metadata-only security notices and purchase indicators do not establish account settings or payments. Record what was observed and use qualified alerts. Collection gaps cannot be repaired into a guaranteed complete action history by resynchronizing current state.
- Add account/resource revision identity, time quality, coverage, evidence provenance and input versioning to the M2 schema review. Derive engine-specific tables incrementally in M3. The raw Messages text retention limit means deterministic replay uses stored extraction; full-text re-extraction and full original-word display cannot be promised.
- The plan's production thresholds are proposals, not measured accuracy. Keep mock tests and controlled real-source validation distinct. Source ambiguity may remain unsolvable; a failed attribution experiment narrows the product claim rather than justifying more confident heuristics.

## Event store implementation, 2026-10-21

- The M2 schema uses `(account, source, resource, revision, kind)` as a non-null event identity. An adapter must supply a stable revision for each distinct Calendar change; reusing an event ID alone would lose updates. Exact retries deduplicate, while conflicting content for the same key is rejected.
- Events carry a schema version, typed payload, source and observation time. Source coverage changes and privacy-minimized received-contact observations are events, so they are available for replay. Collector adapters must validate and minimize their fields before submission; the store also caps event size and source identity lengths.
- The hash chain includes canonical JSON, ordered sequence numbers, a stored head, and a retained-prefix anchor. A single mutable connection owns writes. `picket verify --database` uses a separate read-only connection and reports the first broken sequence, including a removed tail. This detects accidental or casual modification, not a full malicious rewrite of both rows and chain metadata.
- Retention deletes a verified prefix in one transaction with an anchor update and a new checkpoint event. The latest feedback, contact, policy and coverage records are copied forward as typed snapshot events, preserving their replayable current state. A retained checkpoint marks the limited historical horizon; absent older requests or effects cannot be inferred from it.
- M3 uses stable, explicit, non-null finding identities and resource-based incident groups. The M2 migration contains only events and chain state; M3 adds assessment and outbox tables in a separate migration.

## Synthetic alignment foundation, 2026-10-21

- The portable matcher returns separate actor evidence, request fit, account-policy hits, pending state, and route. A successful OpenClaw report links only when account, operation, complete target set, provider resource, and Calendar update revision match. Runtime linkage is conditional on the adapter's honesty; real adapter capability remains untested. Claims stay at `reported` strength and cannot override a runtime link.
- Effects-only observations, external Calendar changes, failed/unlinked tool calls, incomplete targets, multiple plausible tasks, and conflicting runtime links abstain from a named actor or complete request match. Request fields use explicit `Known`, `ExplicitAny`, `Unknown`, and `Ambiguous` states. Matching known fields is only consistency with visible scope, not proof of full authorization.
- A quantity bound is evaluated only when validated runtime reports link each counted effect to the same task. Human account activity does not consume an agent's task allowance; missing task links yield insufficient evidence. Calendar start time and explicit request expiry are hard constraints.
- Account policies are local Picket events with an explicit high-consequence flag. A visible violation can route to review with an unknown actor. Retention snapshots preserve the latest policy as of the cutoff; the replay engine reads the original policy time from the snapshot. Policy editing and confirmation UI remain future work.
- `picket replay --database ... --at ...` verifies the log and prints aggregate counts only. The separate store API persists finding revisions and a notification outbox atomically with inputs, but no collector or OS delivery worker calls it yet. Its synthetic tests are a smoke gate, not the M4 evaluation baseline or measured precision.

## M3 mock engine, 2026-10-21

- Deterministic matching separates actor evidence, visible request fit, account policy, claim consistency, coverage state and alert routing. Claims without a provider ID abstain when more than one similar effect is visible. A lone request with no task link is insufficient for comparison. Baseline imports and observations with unknown origin do not create effect or metadata-notice findings.
- SQLite schema v2 preserves assessment revisions, a processing cursor and a durable notification outbox read in bounded pages. Input, assessment and outbox intent commit in one transaction through `append_assessed`; duplicate input and restart replay do not duplicate alerts. Delivered findings can receive a correction after material late evidence or feedback. Delivery itself belongs to M8.
- Twenty-four labeled synthetic scenarios replay through the store with a scripted `MockModel`; paired cases with identical visible evidence but different true actors remain unknown. These are M3 safety smoke tests. They are not independent validation samples, accuracy estimates or a substitute for the M4 held-out evaluation.
- Optional event fields added during M3 preserve older canonical log entries. Verification checks canonical source JSON and the original hash; a semantically identical retry of an old record deduplicates. Real adapter provenance, source time quality, collection completeness and runtime integrity remain M5/M6 work.

## M4 synthetic evaluation, 2026-10-21

- The M4 baseline is a versioned regression gate over 18 fixed families and 288 constructed cases. It enforces minimum denominators, actor safety, linkage and conflict recall, alert routing, and coverage visibility. Mode and family counts remain separate in the report.
- Variants within a family are correlated. The harness therefore reports raw counts and marks confidence intervals `not_measured`; calculating a binomial interval over 288 constructed variants would imply unsupported independence. Real-source, model, latency, and base-rate measures remain open. No production accuracy target is claimed from M4.

## M5 planning, 2026-10-22

- [M5 Google observation plan](m5-plan.md) records the implementation sequence and verification gates before collector code. The account label in Picket will be locally opaque and bound to the account reported by the allowed Gmail API; the approved scopes do not provide an OpenID subject claim.
- Calendar's documented `events.list` rules forbid `timeMin` and `timeMax` alongside `syncToken`. The bounded baseline and token-bearing initial sync therefore need separate queries. Validate pagination, recurrence and large-calendar behavior with synthetic fixtures and a controlled account before treating coverage as healthy.
- A cursor may advance only in the same committed write as its minimized observations and coverage state. Expired Gmail history or Calendar sync tokens create an explicit gap that current-state resync cannot erase.

## M5 implementation notes, 2026-10-22

- The Google OAuth connection verifies the two granted scopes and Gmail profile, stores a locally opaque account ID with the Keychain refresh credential, and reuses that ID on reauthorization of the same email account. The ID is a local binding, not a Google subject identifier.
- Google observations carry the adapter name, version, approved scope, and source-time quality. Gmail's internal date is provider time. A Calendar record without `updated` uses its ingestion time and is marked as a fallback; malformed provider time fails validation. Older canonical events omit these optional fields and remain verifiable.
- Calendar uses a bounded baseline, a separate unbounded token-bearing initial sync, and a daily bounded window refresh that preserves the incremental cursor. Known events remain tracked when moved outside the window; unknown events outside it are skipped. Source failures and expired cursors produce durable coverage gaps.
- Synthetic collector tests cover retry deduplication, restart, Calendar revision state, expired cursors, invalid source dates, and rolling-window entry. Live OAuth, provider behavior, source-change latency, and actual recurrence edge cases still require the controlled account check before M5 is marked complete.
- The native writer runs the design's default 180-day retention at startup and daily. It preserves a verified chain anchor and current-state snapshots; the later Settings UI can expose the design's user-configurable period.
- The controlled account exposed Gmail's current per-user rate limit during first-run metadata import. The `gmail.metadata` scope cannot use Gmail's date-search parameter, so a complete 30-day baseline may require reading an arbitrarily large mailbox. M5 caps its first scan at 50 listed messages from each of Sent and Inbox, applies the 30-day timestamp filter to fetched metadata, and records a distinct baseline coverage gap when more pages exist. It captures the profile history cursor before the bounded scan and replays history afterward, preserving live changes during bootstrap. Metadata requests are paced and rate-limit responses use exponential backoff. The bounded baseline can leave older contact context incomplete; the UI discloses this limit.

## Incremental assessment and bounded collection, 2026-10-27

A quality review found that monitoring cost grew with the whole retained log. Each Gmail (45 s) and Calendar (60 s) poll appended a fresh healthy coverage event, verified the full hash chain, loaded every event, and reran the engine over all of them; effect assessments embedded coverage as of `now`, so every heartbeat also revised every effect finding. A release-build probe measured 38 ms per reconcile after one simulated day and 410 ms after six, growing superlinearly toward minutes within the 180-day retention. Derived assessment and outbox tables were never pruned. Gmail history beyond 40 pages or 5,000 messages, or a Calendar listing beyond 40 pages, recorded a gap without advancing the cursor and repeated the same failing work indefinitely.

Decisions:

- **The log stays the single source of truth and the engine stays a pure function of visible evidence and time.** Incremental work changes which evidence each assessment reads and when assessments run, not what they conclude. `engine::findings(events, now)` remains the reference replay, and a property test requires incremental results to equal it after every step.
- **Indexes narrow candidates; the original predicates still decide.** The engine reads evidence through in-memory indexes keyed by provider resource, finding, agent, task, account and time. Each index key is a necessary condition of the predicate it serves, so a lookup can only return a superset of the matches the old linear scan found.
- **Explicit dependency rules decide what to reassess.** A new effect, claim, tool result, request, policy, feedback or coverage event reassesses only the findings whose inputs it can change, for example effects sharing its provider resource, effects within the claim window, effects after a request or policy, or the finding named by feedback. Deadlines (an effect's review grace, a claim's observation deadline) are indexed by time. Retention snapshots and checkpoints are housekeeping and trigger nothing.
- **A verdict changes only for a reason: new evidence, a passed deadline, or a new engine version.** Engine state records the last processed sequence and assessment time. A restart processes only later events and deadlines; it does not revise settled findings because retention removed old context. A changed engine version deliberately reassesses everything once.
- **Assessments are anchored to their own decision time, not to `now`.** An effect records coverage as of its review deadline. A claim's "not observed" outcome requires no recorded coverage gap between the claim and the first coverage evidence after its deadline. Once decided, neither changes when later coverage arrives. This removes the global dependency on the latest heartbeat and makes the outcome stable under replay.
- **The log records evidence and state transitions, not liveness.** Collectors report coverage after every poll, and the store logs it only when its state or reason changes, or when an open claim needs a healthy confirmation after its deadline. "Last checked" times stay in the mutable cursor table. The M6 plugin heartbeat follows the same rule. Transient request failures are recorded as `delayed`: catch-up from a valid cursor repairs them, so they appear in the timeline instead of alerting. Lost data (an expired cursor, a missing resource) remains a `gap`, and an authorization failure that needs the user remains review-worthy.
- **Every bounded loop makes durable progress.** Gmail history advances its cursor to the last fully processed history record, and Calendar persists its phase and page token. Each poll has a page and message budget, and a source that is behind continues on the next poll instead of declaring a gap. A healthy confirmation is recorded only once the source has caught up.
- **Retention applies to derived data.** When the log prefix is pruned, findings whose subject event was removed are deleted with their revisions and notification records, and superseded revisions older than the cutoff are pruned unless a pending notification still needs them.
- **Regression tests count work, not wall time.** Scale tests assert that idle polls add no events and that one new input reassesses a bounded number of findings regardless of history size. Timing assertions would be flaky on shared CI runners.

Rejected alternatives: SQL-indexed derived tables (more schema, migrations and duplicated logic for the same bounds); windowed full replay on each poll (still linear per poll and still repeats every finding comparison); time-bucketed heartbeats (fewer events, but still unbounded growth and no exact basis for claim decisions).

Implementation notes, 2026-10-27:

- Effect assessments no longer embed coverage. Coverage remains its own finding, and the future incident view joins the two by account and time. Embedding coverage as of `now` was the dependency that made every heartbeat rewrite every effect verdict.
- `CoverageState::Delayed` covers request failures and token refresh failures with a transport cause; the cursor is intact and catch-up repairs them, so they stay in the timeline. A refresh rejected by Google (`AuthUnavailable`) and lost data (`Gap`) route to review. A delay between a claim and its confirmation does not make the claim incomplete; a gap does.
- Engine version 2 reassesses all findings once after upgrade; schema v5 adds the assessment clock. A write that changes nothing (an idle tick) is skipped, because no deadline passed and an older durable clock only rechecks unchanged subjects on restart.
- The store uses WAL with `synchronous=NORMAL`. A power loss can roll back the latest commits but cannot corrupt the log; cursors roll back with their observations, so the source is read again. This removes an fsync from every poll.
- Gmail history records carry ids; a processed record id is the resume cursor. Each poll reads at most 10 history pages and 100 message metadata requests (about 30 s at the pacing interval). A single record larger than the budget is still processed whole, so every poll advances. Calendar stores a caught-up sync token as itself, as before, and stores the bootstrap phase and page token as tagged JSON otherwise, so existing databases need no migration.
- Equivalence evidence: a temporary differential test matched the indexed engine to the previous linear engine on 80,000 random synthetic histories before semantics changed. The committed property test compares incremental and full replay after every commit and random restarts; mutation runs confirmed that removing any dependency rule fails it, with a targeted test for late task links.
- The portable collector logic still lives in `picket-app`. Move it into `picket-core` behind a shared collector interface at the start of M6, before adding Messages and OpenClaw.
- Session restore after a rejected grant still retries every 30 s with a warning. M8 should surface "reconnect required" instead.
- Gmail web autosave replaces a draft with a new message and deletes the old one, so history lists drafts that are gone before Picket reads them. A missing message that every history entry labels as a draft only is not a send Picket could miss and is not a gap; any other missing message remains a gap. The live check found the false alert this caused for every sent email.

## M6 Messages adapter and E4 request capture, 2026-10-27

- Picket decodes `attributedBody` with its own bounded typedstream reader (the first string object's bytes after a `+` type tag and length). `imessage-database` is GPL-3.0-or-later; avoiding it keeps the project license open and the untrusted parser small.
- Agent registrations are Picket log events, retained as snapshots. Handles are normalized with `phonenumber` (E.164, using the user's region for national numbers) or lower-cased; `chat.db` handles are normalized the same way, so matching never compares raw formats. Only 1:1 conversations are read.
- Message observations store direction, service, text state and a 120-character snippet. Text is never stored; M7 extraction re-reads it from `chat.db` by message identity. Edits and unsends are new revisions of the same message.
- Messages observations belong to the monitored Google account, because v1 compares requests with that account's effects; capture waits until Google is connected.
- "No observed request" now requires `requests_<agent>` coverage: no gap from before the effect until a healthy confirmation after it. Only the request extractor (M7) records it, so until extraction exists an agent-linked effect without a request is `request_not_captured`.
- E4 with Instinct on the owner's Mac, reading only the Instinct 1:1 conversation and printing counts only: a missing Full Disk Access grant was recorded as disabled coverage; granting it started capture without a restart. The 30-day baseline imported 16 messages (4 from the user, 12 from Instinct), all decoded, which the owner confirmed matches the conversation. A live exchange was captured 0.12 s (user) and 2.9 s (Instinct) after the message times. Editing the user's message produced one `edited` revision of the same message 1.2 s later; Instinct's follow-up was a new agent message. Undo Send was not exercised live. Direction is the Messages sender field, not an inference; an agent operating the user's own Messages account would still appear as the user.
- Not yet established: what Instinct's reports contain (actions, recipients, provider ids) and therefore how often claims can be linked to effects. That is part of M7 extraction, using transient text only.

## M7 extraction model and validation, 2026-10-27

- The extractor runs in process through `llama-cpp-2` (MIT or Apache-2.0) with Metal, a fresh context per message, greedy decoding and a grammar generated from the JSON schema. Model files are pinned to a Hugging Face revision and SHA-256 and verified before loading. Qwen publishes no official GGUF for the 4B or 9B models; Picket pins the widely used `lmstudio-community` conversion, and the checksum, not the uploader, is the integrity guarantee.
- The first evaluation of Qwen3.5 4B on the 45-case tuning suite had 20 safety errors. Most came from the schema: separate "state" flags let the model mark actions or recipients as "any" and approval as "not required" without the message saying so. The schema is now values first, and validation widens permission (any action, any recipient, approval not required, a claim from the user's own account) only when the model proposes it and the message's own words say it. Restrictive wording ("don't send", "hold off") always adds a prohibition; a keyword can only restrict, never grant. Names are grounded only outside email addresses, possessives are removed, and a prohibited action is removed from the allowed set after follow-ups merge.
- Because prompt and validation were tuned on `cases.json`, `holdout.json` (30 cases) was written afterwards and run once for model selection: Qwen3.5 4B had 2 safety errors and 4 misses (2.6 s per message), Gemma 4 E4B QAT 3 and 5 (3.2 s), Qwen3.5 9B 3 and 5 (5.3 s), all on an M3 Max. All three failed the same case ("hold off on sending"). Qwen3.5 4B is the default: safest, fastest and smallest (2.7 GB).
- The held-out failure led to adding restrictive cues ("hold off", "not yet"); afterwards Qwen3.5 4B had 0 safety errors on the held-out set and 1 on the tuning set (a reply mistaken for an RSVP, left as a genuine model error). The held-out set is therefore no longer independent; owner-approved live Instinct conversations are the next independent measurement. These are synthetic, correlated cases; no rate is a population estimate.
- A first unscripted live exchange with Instinct on 2026-10-27 found three linkage defects, each fixed with a regression case: Instinct's "Sent from your Gmail" reply names neither task nor recipient, so a recipient-free claim now matches only a unique effect of that action in its window; the claim extractor sees the user's preceding message as labeled context, used only to choose the open task, and agent-unnamed recipients are dropped; and a model's task link is kept only when it equals the task that preceding message created or revised. Derived records now carry their extraction time separately from the message time. No accuracy is claimed from that exchange; the scripted live run remains the independent measurement.
- Keyword fallback, listed in the original M7 milestone, is not implemented (M7 plan, decision 10). Without the model, request capture stays unhealthy and findings say the request channel was not captured.

## Fixes after the live run, 2026-11-02

- Extraction offers the model only the task under discussion: the latest revision of the task that the user's most recent request created or revised, unless cancelled. A revision can only be of that task, and an agent reply links only to it. Every follow-up in the live run referred to that task; returning to an older task becomes a standalone request, which is less precise but cannot attach permission to the wrong task.
- An approval or cancellation needs the model's proposal and the person's words ("yes", "send it", "go ahead"; "cancel", "never mind"). With those, a short reply applies to the current task even when the model calls it a new task, as it did for "Yes send". The request schema no longer carries a task id.
- A claim needs an unnegated completion word for its action or a general one ("done", "all set") within its own text; questions, plans, refusals and "not sent" claim nothing. This check only removes claims. A claim is placed in the agent's own mailbox only with words such as "from my".
- A claim without a provider id covers the span after the same agent's previous claim of the same action, at most ten minutes back and two minutes forward, and needs one matching effect there. The ten-minute window alone could not separate sends six minutes apart.
- The user's own attendee entry, and the organizer of an event the user organized, are not Calendar recipients.
- Qwen3.5 4B on this Mac, prompt version 2: the new follow-up suite (28 cases, synthetic paraphrases of the live failures, written after the run) had 0 safety errors and 3 misses; the tuning suite 0 and 7; the held-out suite 0 and 6, against 1 and 2 safety errors before. All three are tuning evidence now. Without runtime counts, a reported Instinct send linked to its task is assessed as "insufficient evidence", never "consistent"; that is the design's quantity rule, not a defect. The next scripted live run is the independent check.

## Replay and generalization check, 2026-11-02

- `picket replay-extraction` re-ran the live conversation through the current extractor in a scratch store. After the replay fixes (a request naming its own recipient and action is its own task; an approval naming an action lifts that action's prohibition on the task; a report whose hinted task did not exist when the effect happened is judged against the task under discussion then), all three Instinct sends were linked to their own tasks without conflict, the cancellation was recorded, and every "Sent." matched its send. Remaining in the replay: two Calendar extra-target conflicts from effects stored before the self-attendee fix (replay does not recollect effects), the named recipient of step 2 not captured, and one clarifying message extracted as a task. The four undecodable messages all contained links, archived as `NSMutableString`; all four decode with the fixed decoder.
- `eval/extraction/generalization.json` (38 cases) was written after these changes with phrasings and agent styles absent from every prompt example and earlier suite, and run once without tuning: 1 safety error, 9 misses. The safety error is "Send it to ana@example.test instead" counted as approving the current task, because "send it" is an approval cue; the label is debatable, but it shows the approval cue list matches action phrases. Misses: two approvals ("Fine by me, send", "Please do"), three agent reports with no listed completion word ("Fired off the email", "The meeting is now at 4pm", "Already sent that one"), two times, and one follow-up. The structural rules held: follow-ups, cancellations in other words, new versus follow-up, and questions, refusals and errors producing no claim.
- Conclusion: the task, linkage and Calendar rules are general; the approval and completion word lists are the brittle part and fail toward "unknown", not toward granting permission or inventing a report, with the one approval exception above. This suite is now spent as a held-out measure once anything is tuned against it; an owner-written set of phrasings is the next independent check.

## Quoted evidence instead of keyword lists, 2026-11-02

- Why change: keyword lists for approvals and completed reports missed natural wording ("fine by me", "fired off the email") and matched action phrases as approvals ("send it to Ana instead"). The model understands language better than a list; it is not reliable enough to be trusted alone, so it now quotes its evidence and Rust checks the quote mechanically.
- Approvals: the model proposes the approval with the person's exact words; the words must appear in the message, must not be negated, and a separate narrow question ("do these words give the go-ahead for this task as it stands?") must be answered yes. This second question added real judgment: it accepted "Looks good, ship it" and "Fine by me, send" and refused "send them the invite too" as approving an email task.
- Skipping the check, any recipient and any action: the quote must contain an explicit phrase ("no need to", "anyone", "whoever", "up to you"). The second question approved "whoever on the team should know" as leaving the action open, so it is not used for these; explicit wording is the right bar for broad permissions.
- Reports: the model quotes the agent's words; the quote must lie in one sentence that is not a question and has no negation and no future, offer or attempt word in or just before it, checked with small closed sets of function words. A second question rejected plain reports ("Sent.", "I declined the invite"), so it is not used. "Your" or "my" in a quoted phrase places an email in the person's or the agent's mailbox.
- Follow-ups keep their task's kind (email or calendar). A short reply that the model reads as approving or cancelling stays with the task and loses a mismatched action; any other request for the other kind becomes a new task that inherits nothing. A second question about added actions only echoed the model and was dropped.
- Results, Qwen3.5 4B on this Mac, prompt version 3, 149 cases in four suites: 1 safety error and 25 misses, the same totals as the keyword version; on the phrasings suite 0 and 3 against 1 and 9, but that suite was used while tuning and no longer measures generalization. The remaining error is the model reading "just create the draft" as a calendar request; with the live task's prohibition it now becomes a separate calendar task rather than permission on the email task, but it is still a model misreading no check here catches. About 4.6 s per message.
